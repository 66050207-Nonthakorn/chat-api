# ข้อสรุปการออกแบบและงานที่เลื่อนไประยะถัดไป

> ฉบับละเอียดก่อนย่อ Notion เก็บเมื่อ 2026-10-28
> เอกสารแผนและข้อสรุป ไม่ใช่หลักฐานว่าพัฒนา ทดสอบ หรือ deploy สำเร็จ
> ที่มา: [หน้า Notion](https://www.notion.so/40376688030081f98f64d898d7821ad4) — ปัจจุบันเป็นฉบับย่อ

**สถานะ: ข้อสรุปที่เจ้าของโครงการยืนยันแล้ว ไม่ใช่หลักฐานว่าพัฒนาเสร็จ**
ปรับปรุงเมื่อ 2026-10-25 หน้านี้เป็นแหล่งอ้างอิงข้อสรุปชุดเดียว รวมสาระจากหน้าตัดสินใจเดิมไว้แล้ว ขอบเขตขั้นต่ำเพื่อสาธิตโครงสร้างพื้นฐานมีลำดับความสำคัญเหนือการทำฟีเจอร์ครบ

## รูปแบบโปรแกรมและความถูกต้องของข้อความ

- **D01 — Modular monolith:** แอป Go เดียวที่แบ่งโมดูลภายใน รันหลาย replica ได้ เลือกเพื่อให้การพัฒนา การทดสอบ และ transaction ตรงไปตรงมา แทนการแยก gateway หรือ microservices ตั้งแต่แรก ข้อแลกเปลี่ยนคือโมดูลปล่อยเวอร์ชันร่วมกัน และการขยาย socket เพิ่มส่วน HTTP ไปด้วย
- **D02 — บันทึกก่อนตอบรับ:** ตอบสำเร็จหลัง transaction commit เท่านั้น ลองคำขอเดิมซ้ำต้องได้ผลเดิม การได้รับหรืออ่านข้อความของผู้รับเป็นคนละสถานะ ข้อแลกเปลี่ยนคือรอการเขียนฐานข้อมูลและรับข้อความใหม่ไม่ได้เมื่อฐานข้อมูลใช้ไม่ได้
- **D03 — PostgreSQL:** เป็นแหล่งข้อมูลอ้างอิงสำหรับข้อความและข้อมูลถาวรที่สัมพันธ์กัน รองรับ transaction และ constraint แทน DynamoDB/MongoDB ข้อแลกเปลี่ยนคือดูแล schema, index, connection pool และความจุ
- **D04 — ลำดับเดียวต่อห้อง:** ทุกอุปกรณ์ใช้ลำดับข้อความที่เซิร์ฟเวอร์กำหนด ไม่รับรองลำดับรวมทั้งแอป ห้องที่ส่งถี่อาจรอการจัดลำดับ
- **D05 — ส่งสดแบบ best-effort และกู้จากฐานข้อมูล:** เน้นความเร็วของการแจ้งเตือน แต่ต้อง sync เมื่อเชื่อมต่อใหม่ พบช่องว่าง และตามรอบขณะเปิดแอป socket ที่เชื่อมอยู่ไม่ได้รับรองว่าจะไม่พลาดเหตุการณ์
- **D06 — Transactional outbox:** บันทึกงานแจ้งเตือนพร้อมข้อความ กู้คืนช่องว่างระหว่าง commit กับ publish ได้ แลกกับตาราง งานเบื้องหลัง retry และการจัดการเหตุการณ์ซ้ำ
- **D07 — Valkey/Redis Pub/Sub:** แยกภาระส่งสดออกจาก PostgreSQL แลกกับอีก dependency และการยอมรับว่า notification สูญหายได้
- **D17 — Go:** เหมาะกับการจัดการงานพร้อมกันและโปรแกรม backend ที่ชัดเจน ต้องควบคุม goroutine, cancellation และ shared state เลือกแทน TypeScript/Node.js หรือ Java/Spring
- **D18 — HTTP สำหรับคำสั่งถาวร และ WebSocket สำหรับเหตุการณ์สด:** สัญญาคำขอ/คำตอบตรวจสอบง่าย แต่ไคลเอนต์ต้องรวมผล HTTP กับเหตุการณ์ที่อาจมาถึงก่อน
- **D28 — Go worker แยกบน Fargate:** แยกการเริ่ม/หยุดและขนาด publisher ใช้โค้ด/image/ฐานข้อมูลร่วมกับแอป ข้อแลกเปลี่ยนคืออีก ECS service ไม่ใช่การแยกกฎธุรกิจเป็น microservice
- **D35 — ช่อง Pub/Sub ร่วมต่อ environment:** replica รับเหตุการณ์แล้วส่งเฉพาะผู้รับในเครื่องที่ผ่านสิทธิ์ ไม่ต้องมี directory ผู้ใช้ต่อเครื่อง แลกกับ traffic และการกรองที่โตตามจำนวน replica ค่อยเปลี่ยนเป็นช่องต่อห้องหรือส่งตรงเมื่อมีผลวัด

## ตัวตน สิทธิ์ และสมาชิก

- **D08 — Cognito:** ใช้บริการจัดการตัวตน แทนการดูแล Keycloak หรือรหัสผ่านเอง ข้อเสนอเอา Cognito ออกถูกถอนแล้ว ต้องคง Cognito
- **D09 — Backend-managed session:** backend จัดการแลกและเก็บ token เบราว์เซอร์ได้รหัส session ใน Secure/HttpOnly cookie ต้องป้องกัน CSRF และตรวจ Origin
- **D10 — Session ใน PostgreSQL:** ใช้ร่วมกันข้าม replica และไม่หายตาม cache แลกกับภาระตรวจฐานข้อมูล การหมดอายุ cleanup และการประสาน refresh
- **D11 — ตรวจสิทธิ์จากข้อมูลอ้างอิงจริง:** ตรวจสมาชิกปัจจุบันกับ PostgreSQL ก่อนส่ง อ่าน sync subscribe และอนุญาตส่งสด การตรวจที่เริ่มหลังลบสมาชิก commit ต้องปฏิเสธ แต่ข้อมูลที่อนุญาตหรืออยู่ระหว่างส่งอาจถึงผู้รับได้
- **D12 — สมาชิกปัจจุบันอ่านประวัติทั้งหมด:** รวมถึงสมาชิกที่กลับเข้ามา การเพิ่มคนเปิดเผยประวัติก่อนหน้าให้คนนั้น การลบสมาชิกหยุดสิทธิ์ฝั่งเซิร์ฟเวอร์แต่ลบสำเนาที่ดาวน์โหลดแล้วไม่ได้
- **D13 — แอปชุมชนเดียว:** มี DM และกลุ่มปิด ไม่มี workspace หลายองค์กร
- **D14 — เข้าร่วมด้วยคำเชิญและมีรายชื่อภายใน:** ไม่เปิดสมัครสาธารณะ เดโมเตรียมบัญชีไว้ได้โดยไม่ต้องทำหน้าจัดการทั้งหมด ฟิลด์ข้อมูลที่แสดงยังต้องระบุ
- **D15 — เจ้าของ/ผู้ดูแลจัดการสมาชิก:** เจ้าของและผู้ดูแลจัดการสมาชิกทั่วไป เฉพาะเจ้าของแต่งตั้งผู้ดูแล ผู้ดูแลลบเจ้าของไม่ได้ เจ้าของโอนสิทธิ์ก่อนออก สมาชิกออกเองได้
- **D33 — เก็บประวัติตลอดช่วงโครงการ:** ไม่ลบตามอายุอัตโนมัติในระยะแรก ล้างโดยตั้งใจพร้อมกำหนดว่าจะเก็บ snapshot/export ต่อหรือไม่
- **D34 — Secrets Manager:** เก็บข้อมูลรับรองบริการนอก source/image แยกจาก config ทั่วไป token รายผู้ใช้ยังอยู่ใน PostgreSQL ไม่ใช่ secret แยกต่อคน ต้องกำหนดการหมุนเวียนและโหลดค่าใหม่

## โฮสติ้ง การปล่อยเวอร์ชัน และการติดตามระบบ

- **D19 — ECS/Fargate:** ให้ AWS ดูแล compute ของ container แทนการจัดการ host EC2 หรือ Kubernetes
- **D20 — RDS PostgreSQL:** ฐานข้อมูล PostgreSQL แบบ managed แทน Aurora หรือดูแลฐานข้อมูลเอง
- **D21 — แยกรูปแบบพัฒนากับสาธิต:** พัฒนาใช้ Single-AZ RDS และสาธิตความทนทานใช้ Multi-AZ พร้อม standby ภายใต้สิทธิ์และเครดิตที่ต้องตรวจจริง
- **D22 — ElastiCache แบบ node:** เลือก topology ชัดเจนแทน serverless หรือ self-hosted ค่า estimate ใช้ Valkey เป็นข้อเสนอ ส่วน engine/version ขนาดและจำนวน replica ต้องยืนยัน
- **D23 — Rolling deployment:** ค่อยแทน task ที่พร้อมใช้งาน รองรับเวอร์ชันซ้อนกัน rollback และ reconnect ไม่รับรองว่า socket ไม่หลุด
- **D24 — Terraform:** สร้างโครงสร้างพื้นฐานจากนิยามที่ตรวจแผนก่อนใช้ได้ แทน CDK หรือ CloudFormation ตรง ๆ ต้องป้องกัน state และแยก environment
- **D25 — Backend อยู่ private subnet:** รับผ่าน ALB สาธารณะ ข้อมูลอยู่ private และต้องจัดเส้นทางออกซึ่งมีต้นทุน NAT/endpoint
- **D26 — Svelte + TypeScript + Vite:** เรนเดอร์ในเบราว์เซอร์และเผยแพร่ไฟล์ static ไปยัง S3 + CloudFront ตามข้อสรุปเดิม เปลี่ยนจาก React เป็น Svelte ตามที่เจ้าของเลือกเมื่อ 2026-10-28
- **D27 — S3 + CloudFront:** แยกการปล่อย frontend ใช้ origin เดียวผ่านเส้นทาง API/auth/WS ไป ALB ต้องตั้ง cache, cookie และ header ให้ถูกต้อง แทนเสิร์ฟไฟล์จาก Go
- **D29 — GitHub Actions:** pipeline อยู่กับ repository GitHub ใช้ OIDC รับสิทธิ์ AWS ชั่วคราวแบบจำกัดขอบเขต
- **D30 — Dev อัตโนมัติ สาธิตเลื่อนด้วยมือ:** deploy พัฒนาเมื่อ environment มีอยู่ ใช้ artifact เดิมที่ผ่านแล้วไปสาธิต ไม่สร้าง environment เพราะ push โค้ด
- **D31 — ระบบติดตามแบบ managed ของ AWS:** CloudWatch สำหรับ log/metric/dashboard/alarm และ OpenTelemetry สำหรับ trace ที่ส่งไป AWS ต้องจำกัด sampling, retention และจำนวน label
- **D32 — จำนวน task คงที่ก่อน autoscaling:** วัดก่อนตั้ง policy ที่มีเพดาน แยก API กับ worker เคารพขีดจำกัด connection ฐานข้อมูล และระบาย socket เมื่อ scale-in
- **D40 — วัดเป็นขั้น:** พื้นฐาน 100 connections / 10 ข้อความต่อวินาที / กลุ่มไม่เกิน 20 คน ทดลองเพิ่มเป็น 1,000 / 100 / 100 ตามลำดับ เป็นเป้าทดสอบ ไม่ใช่ผลสำเร็จหรือ SLA
- **D41 — Local-first และเปิด AWS เมื่อต้องใช้:** ใช้ช่วง integration ซ้อม และสาธิตแล้วล้างทรัพยากร ระบบต้องรัน local ได้โดยไม่มี AWS

## พฤติกรรมไคลเอนต์และฟีเจอร์ระยะถัดไป

- **D16 — ข้อความยังแก้ไข/ลบไม่ได้ใน milestone แรก:** เพิ่มภายหลังพร้อมสัญญากู้คืนการเปลี่ยนแปลง
- **D36 — เก็บข้อความรอยืนยันในเบราว์เซอร์:** ใช้รหัสเดิมหลัง refresh/retry แยกตามผู้ใช้ ล้างเมื่อ logout จัดการกรณี storage ล้มเหลว และไม่แสดงว่ารับสำเร็จก่อนเซิร์ฟเวอร์ยืนยัน
- **D37 — ตำแหน่งอ่านร่วมระดับผู้ใช้:** ขยับไปข้างหน้าอย่างเดียวต่อห้อง แต่ตำแหน่ง sync ของแต่ละอุปกรณ์แยกกัน
- **D38 — ใบตอบรับการอ่านเฉพาะ DM:** ตำแหน่งอ่านในกลุ่มเป็นข้อมูลส่วนตัวสำหรับนับข้อความที่ยังไม่อ่าน
- **D39 — กำลังพิมพ์และออนไลน์โดยประมาณ:** เป็นข้อมูลชั่วคราวหมดอายุได้ ไม่มีประวัติ last-seen และเพิ่มหลังแกนข้อความทำงานแล้ว

D37-D39 รวมถึง UI จัดการกลุ่ม/คำเชิญ/รายชื่อถูกเลื่อนจากเดโมขั้นต่ำ นโยบายยังคงยอมรับแล้ว แต่ไม่ใช่งานที่ต้องทำก่อนสาธิตคลาวด์

## ขอบเขตและงบประมาณฉบับล่าสุด

เจ้าของยืนยันเดโมขั้นต่ำตาม rubric: เข้าสู่ระบบ ผู้ใช้/ห้องที่เตรียมไว้ ข้อความและประวัติ การ reconnect ส่งสดข้าม replica กู้ worker ปล่อยเวอร์ชัน และ dashboard เน้นโครงสร้างพื้นฐานมากกว่าฟีเจอร์

การคุยประมาณราคาก่อนตั้งงบ (D42) และน้ำหนักเดโม (D43) ถูกสรุปด้วยขอบเขตข้างต้นและเป้าหมายจ่ายเองใกล้ศูนย์ ข้อเสนอให้สำรองเงินส่วนตัว USD 50 **ไม่ได้รับการยอมรับและไม่ใช่งบที่อนุมัติ**

เลือก **AWS Free account plan และคงสถาปัตยกรรมเดิม** สมัครภายหลัง เครดิต วันหมดอายุ บริการที่ใช้ได้ region และ quota ยังไม่ตรวจ การใช้เครดิตคือต้นทุนตามมิเตอร์ ไม่ใช่การใช้บริการฟรีถาวร

ยังไม่อนุมัติให้เปลี่ยนเป็น Lambda/DynamoDB เอา Cognito ออก อัปเกรดบัญชีแบบเสียเงิน ซื้อโดเมน หรือสร้างทรัพยากร

## เหตุผลและทางเลือกของข้อสรุปพื้นฐาน

**Modular monolith:** microservices แยก deploy/scale ได้ละเอียดกว่า แต่เพิ่มการเรียกข้ามเครือข่าย การจัดการสิทธิ์และ transaction ข้ามบริการ ส่วน gateway แยกช่วยแยก connection load แต่เพิ่ม deployment และความเข้ากันได้ของสัญญา จึงเริ่มโมดูลในแอปเดียวและแยก worker ตามบทบาท

**บันทึกก่อนตอบรับ:** การเข้าคิวถาวรก่อนบันทึกช่วยรองรับ burst แต่สถานะเข้าคิวไม่เท่ากับมีในประวัติและเพิ่ม broker ในเส้นทางสำคัญ การส่งสดก่อนบันทึกมีช่วงที่ผู้รับเห็นข้อความแต่ประวัติอาจไม่ถูกเก็บ จึงเลือกฐานข้อมูล commit ก่อน ความสำเร็จของ socket send ไม่ใช่ความสำเร็จของการบันทึก

**PostgreSQL:** ความสัมพันธ์ผู้ใช้/ห้อง/สมาชิกและการเขียนพร้อมกันเหมาะกับ relational transaction, unique และ foreign key ส่วน DynamoDB ต้องออกแบบ access pattern/key และ consistency ล่วงหน้า MongoDB ต้องตัดสินใจ embedding/reference สำหรับความสัมพันธ์หลายต่อหลาย ทั้งสองทำได้แต่ยังไม่มีประโยชน์ชัดกว่าสำหรับความต้องการนี้ การกระจาย write หลายเซิร์ฟเวอร์ของ PostgreSQL ต้องออกแบบเพิ่ม
