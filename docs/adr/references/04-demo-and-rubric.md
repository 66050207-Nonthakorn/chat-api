# แผนสาธิตและหลักฐานตามเกณฑ์คะแนน

> ฉบับละเอียดก่อนย่อ Notion เก็บเมื่อ 2026-10-28
> เอกสารแผนและข้อสรุป ไม่ใช่หลักฐานว่าพัฒนา ทดสอบ หรือ deploy สำเร็จ
> ที่มา: [หน้า Notion](https://www.notion.so/40376688030081e8adf2ef9a8fc67ac2) — ปัจจุบันเป็นฉบับย่อ

**สถานะ: แผนเก็บหลักฐาน ยังไม่มีผลทดสอบหรือคะแนนที่ยืนยันแล้ว**
อ้างอิงไฟล์เกณฑ์การให้คะแนนโครงการภาษาไทยหนึ่งหน้าที่เจ้าของส่งในแชท ตรวจเมื่อ 2026-10-25 เกณฑ์เป็นข้อกำหนด ไม่ใช่หลักฐานว่าโครงการทำผ่านแล้ว

## การเชื่อมโยงกับคะแนน

| หัวข้อ | คะแนน | หลักฐานของโครงการ |
| --- | --- | --- |
| ข้อเสนอโครงการและแผนงาน | 5 | ปัญหา ผู้ใช้ ขอบเขตที่ทำและไม่ทำ milestone รายสัปดาห์ ความปลอดภัย และแผนควบคุมต้นทุน/เครดิต |
| สถาปัตยกรรมและการออกแบบคลาวด์ | 15 | แผนภาพ AWS เครือข่ายและการไหลข้อมูลถูกต้อง มี Fargate เป็น Compute, S3 เป็น Storage และ RDS เป็น Database มีการขยายตัวหรือ HA ฐานข้อมูล private และแยกข้อมูลรับรองจากโค้ด |
| ระบบสาธิตการทำงานจริง | 15 | ใช้งาน HTTPS/WSS บนคลาวด์จริง ข้อมูลผ่านบริการครบ ประมวลผลทดแทนได้และเก็บสถานะภายนอก พร้อม IAM และการติดตั้งที่ใช้งานได้ |
| การนำเสนอและการให้เหตุผล | 10 | อธิบายแต่ละบริการว่าคืออะไร ทำหน้าที่อะไร และทำไมเลือก พร้อมข้อแลกเปลี่ยนกับทางเลือกที่เหมาะสม |
| การถาม–ตอบ | 5 | อธิบายเจ้าของข้อมูล หลักประกันการส่ง ความเสียหาย สิทธิ์ การขยายตัว และการล้างทรัพยากร |
| คะแนนพิเศษ | รวม +5 | CI/CD ครบ การสาธิต rolling/blue-green และ dashboard ดู metric/log สด เอกสารไม่ได้แบ่งคะแนนพิเศษแยกต่อรายการ |

เกณฑ์ระบุการขยายตัว **หรือ** ความพร้อมใช้สูง ไม่ได้กำหนดว่าต้องทำการทดลองขั้นสูงทุกชนิด คงแผน autoscaling และ Multi-AZ ที่เลือกไว้ แต่จัดลำดับให้ระบบหลักและหลักฐานคะแนนพิเศษพร้อมก่อน ภายใต้เครดิตและเวลาจริง

ไฟล์ frontend บน S3 ตอบโจทย์ static/object storage แล้ว ไม่จำเป็นต้องทำไฟล์แนบ socket และ subscription ในหน่วยความจำเป็นสถานะชั่วคราว ส่วนข้อความ session และ outbox ต้องอยู่ภายนอก task เพื่อทดแทน compute ได้

## ลำดับสาธิตขั้นต่ำ

1. **ภาพรวม:** ชี้ CloudFront/S3, ALB/public subnet, Go task/private subnet, RDS/ElastiCache, worker, IAM และ secrets
2. **กรณีใช้งานจริง:** เข้าสู่ระบบ ส่งระหว่างไคลเอนต์บน API คนละ task แสดง HTTP ตอบรับหลัง commit และ notification ผ่าน WSS
3. **สถานะภายนอกและการแยกงาน:** แสดงข้อความ/outbox ในฐานข้อมูล หยุด worker ดูอายุงานค้าง แล้วเริ่มใหม่ให้ทำต่อ
4. **กู้ replica:** หยุด API task ดู reconnect/resubscribe/sync และเทียบรหัสข้อความที่ตอบรับกับ PostgreSQL
5. **ปล่อยเวอร์ชัน:** รัน GitHub Actions ที่เตรียมไว้ แสดง task revision เก่า/ใหม่ traffic ทดสอบ metric reconnect และข้อความที่ยังอยู่
6. **ปฏิบัติการ:** เปิด dashboard, log และ trace อธิบายช่วงสะดุดที่วัดได้
7. **ผลประเมินและต้นทุน:** แสดงผลโหลด/failover พร้อมข้อจำกัด อธิบายเครดิต Free plan และการ teardown

เป็นลำดับเสนอ ไม่ใช่เวลานำเสนอที่ยืนยันแล้ว ต้องปรับตามคาบจริง ซ้อม จัดเวอร์ชัน rollback และเตรียมวิดีโอ/หลักฐานสำหรับการทดลองที่ใช้เวลารอ

## ตารางหลักฐานการตรวจรับ

| การทดลอง | ผลที่คาดหวัง | หลักฐานที่เก็บ |
| --- | --- | --- |
| แชทข้าม replica | ผู้รับที่ผ่านสิทธิ์บน task อื่นได้รับสด | รหัส task รหัสและลำดับข้อความ และ trace การรับ |
| คำตอบหายหลัง commit | ลองรหัสเดิมแล้วมีข้อความเดียว | จุดแทรกความผิดพลาด ผล retry และการตรวจความไม่ซ้ำในฐานข้อมูล |
| หยุด publisher | ข้อความยังบันทึก งานค้างสะสมแล้วกู้คืนได้ | กราฟอายุ/จำนวน outbox และจำนวนงานที่ทำต่อ |
| เผยแพร่ซ้ำ | ไม่สร้างข้อความซ้ำเชิงตรรกะบนหน้าจอ | ทดสอบหยุดหลัง publish และเทียบไคลเอนต์กับฐานข้อมูล |
| เหตุการณ์ broker หายเงียบ | sync ตามรอบพบข้อความสุดท้ายที่หายโดย socket ไม่ต้องหลุด | ช่วงตัด subscriber และเวลาที่ข้อมูลกลับมาตรงกัน |
| API task ล่ม | เชื่อมต่อใหม่และกู้ข้อความที่ตอบรับแล้ว | กราฟ disconnect/reconnect และรายการรหัสที่ควรมี |
| Rolling deployment | มีบริการที่พร้อมรับงานต่อเนื่อง socket ที่ถูกปิดกลับมาได้ | pipeline, revision, request error, reconnect และผลตรวจข้อมูล |
| การขยายระบบ | วัดค่าคงที่ก่อน แล้วเพิ่มความจุด้วย policy ที่มีเพดาน | โหลด/config จำนวน task ความอิ่มตัว latency และ error |
| ซ้อม RDS failover | ไม่ตอบรับสำเร็จเท็จ และทำงานต่อหลังฐานข้อมูลกลับมา | RDS event, retry, connection recovery และผลเทียบข้อความ |
| การเข้าถึงไม่มีสิทธิ์ | ปฏิเสธ send/history/sync/subscribe และการส่งสด | negative test รวมถึงการลบสมาชิกชนกับการส่ง |

## ขอบเขตคำกล่าวอ้าง

ต้องไม่มีข้อความที่ตอบรับแล้วสูญหายในกรณีเสียหายที่ทดสอบ ไม่อ้างว่ารอดทุกภัยพิบัติหรือมี SLA ที่ยังไม่วัด การพร้อมใช้ของบริการระหว่าง rolling ไม่แปลว่า socket ทุกเส้นไม่หลุด การ publish สำเร็จไม่ใช่หลักฐานว่าอุปกรณ์รับแล้ว การมี autoscaling/Multi-AZ ใน Terraform ไม่ใช่ผลยืนยันว่าทำงานผ่าน

แยกผลเป้าพื้นฐานกับเป้าทดลองเพิ่มเติม ระบุ p50/p95/p99, error, backlog, ทรัพยากร เวลากู้คืน config ขนาดข้อความ สัดส่วน traffic และเวลาทดสอบ เกณฑ์ latency เชิงตัวเลขต้องตกลงจาก rubric และผลจริง ไม่แต่งขึ้น

## ประเด็นอธิบายบริการและทางเลือก

- **Fargate:** รัน container API/worker โดยไม่ดูแล host เปรียบเทียบ ECS/EC2 และ Kubernetes
- **RDS PostgreSQL:** เก็บข้อมูล transaction ที่เป็นแหล่งอ้างอิง เปรียบเทียบ Aurora และการดูแลเอง
- **S3:** เก็บ object ของ frontend เปรียบเทียบไฟล์ใน task กับ file storage ร่วม
- **CloudFront:** ส่งไฟล์และรวม browser origin เปรียบเทียบเสิร์ฟไฟล์จาก Go
- **ALB:** รับ HTTPS/WebSocket ไป task ที่พร้อม ไม่ใช่ที่เก็บข้อความ
- **ElastiCache Pub/Sub:** แจ้งเหตุการณ์ข้าม replica รวดเร็ว เปรียบเทียบ polling ฐานข้อมูลและ durable stream
- **Outbox:** เก็บงานเผยแพร่ที่กู้คืนได้ อธิบายช่องว่าง commit/publish และเหตุการณ์ซ้ำ
- **Cognito/session:** แยกตัวตน session ของแอป และสิทธิ์ห้องสนทนา
- **Terraform/GitHub Actions:** สร้างซ้ำและปล่อยเวอร์ชันทดสอบแล้ว แยก infra plan จากการเลื่อนแอป
- **CloudWatch/OpenTelemetry:** เก็บผลที่สังเกตได้และวิเคราะห์ปัญหา พร้อมอธิบายต้นทุน telemetry
