# แกนข้อความถาวรและการส่งสดข้าม replica

เลือก Go modular monolith, PostgreSQL, commit ก่อนตอบรับ และ transactional outbox ร่วมกับ Valkey/Redis Pub/Sub เพื่อให้ข้อความที่ยอมรับแล้วกู้จากฐานข้อมูลได้ แม้ API/worker หยุดหรือ notification สูญหาย

- **บันทึก:** 2026-10-28 จากข้อสรุปเดิมในบทสนทนา/Notion ไม่ใช่การตัดสินใจใหม่
- **สถานะการพัฒนา:** ยังไม่มีผลตรวจรับยืนยันในเอกสารต้นทาง

## ข้อสรุปและข้อแลกเปลี่ยน

- **D01 — Modular monolith:** แอป Go เดียวที่แบ่งโมดูลภายใน รันหลาย replica ได้ เลือกเพื่อให้การพัฒนา การทดสอบ และ transaction ตรงไปตรงมา แทนการแยก gateway หรือ microservices ตั้งแต่แรก ข้อแลกเปลี่ยนคือโมดูลปล่อยเวอร์ชันร่วมกัน และการขยาย socket เพิ่มส่วน HTTP ไปด้วย
- **D02 — บันทึกก่อนตอบรับ:** ตอบสำเร็จหลัง transaction commit เท่านั้น ลองคำขอเดิมซ้ำต้องได้ผลเดิม การได้รับหรืออ่านข้อความของผู้รับเป็นคนละสถานะ ข้อแลกเปลี่ยนคือรอการเขียนฐานข้อมูลและรับข้อความใหม่ไม่ได้เมื่อฐานข้อมูลใช้ไม่ได้
- **D03 — PostgreSQL:** เป็นแหล่งข้อมูลอ้างอิงสำหรับข้อความและข้อมูลถาวรที่สัมพันธ์กัน รองรับ transaction และ constraint แทน DynamoDB/MongoDB ข้อแลกเปลี่ยนคือดูแล schema, index, connection pool และความจุ
- **D04 — ลำดับเดียวต่อห้อง:** ทุกอุปกรณ์ใช้ลำดับข้อความที่เซิร์ฟเวอร์กำหนด ไม่รับรองลำดับรวมทั้งแอป ห้องที่ส่งถี่อาจรอการจัดลำดับ
- **D05 — ส่งสดแบบ best-effort และกู้จากฐานข้อมูล:** เน้นความเร็วของการแจ้งเตือน แต่ต้อง sync เมื่อเชื่อมต่อใหม่ พบช่องว่าง และตามรอบขณะเปิดแอป socket ที่เชื่อมอยู่ไม่ได้รับรองว่าจะไม่พลาดเหตุการณ์
- **D06 — Transactional outbox:** บันทึกงานแจ้งเตือนพร้อมข้อความ กู้คืนช่องว่างระหว่าง commit กับ publish ได้ แลกกับตาราง งานเบื้องหลัง retry และการจัดการเหตุการณ์ซ้ำ
- **D07 — Valkey/Redis Pub/Sub:** แยกภาระส่งสดออกจาก PostgreSQL แลกกับอีก dependency และการยอมรับว่า notification สูญหายได้
- **D17 — Go:** เหมาะกับการจัดการงานพร้อมกันและโปรแกรม backend ที่ชัดเจน ต้องควบคุม goroutine, cancellation และ shared state เลือกแทน TypeScript/Node.js หรือ Java/Spring
- **D18 — HTTP สำหรับคำสั่งถาวร และ WebSocket สำหรับเหตุการณ์สด:** สัญญาคำขอ/คำตอบตรวจสอบง่าย แต่ไคลเอนต์ต้องรวมผล HTTP กับเหตุการณ์ที่อาจมาถึงก่อน
- **D28 — Go worker แยกบน Fargate:** แยกการเริ่ม/หยุดและขนาด publisher ใช้โค้ด/image/ฐานข้อมูลร่วมกับแอป ข้อแลกเปลี่ยนคืออีก ECS service ไม่ใช่การแยกกฎธุรกิจเป็น microservice
- **D35 — ช่อง Pub/Sub ร่วมต่อ environment:** replica รับเหตุการณ์แล้วส่งเฉพาะผู้รับในเครื่องที่ผ่านสิทธิ์ ไม่ต้องมี directory ผู้ใช้ต่อเครื่อง แลกกับ traffic และการกรองที่โตตามจำนวน replica ค่อยเปลี่ยนเป็นช่องต่อห้องหรือส่งตรงเมื่อมีผลวัด

## เงื่อนไขที่ต้องรักษา

- ใช้ HTTP สำหรับคำสั่งถาวร และ WebSocket สำหรับเหตุการณ์สด
- Retry รหัสเดิมต้องไม่สร้างข้อความใหม่; ลำดับอ้างอิงอยู่ต่อห้อง
- Lease/retry กู้ worker ได้; publish อาจซ้ำจึงต้อง dedup
- Sync หลัง reconnect/พบช่องว่าง/ตามรอบ และใช้ cursor ต่อเนื่องล่าสุด
- ทางเลือก microservices/gateway แยกเพิ่ม network/auth/transaction; queue-first หรือ live-first ไม่ยืนยันว่ามีในประวัติ
- ห้องส่งถี่อาจติด lock; PostgreSQL กระจาย write หลายเครื่องต้องออกแบบเพิ่ม
